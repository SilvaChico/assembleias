# Proposal vote codes

Participants enter at `/` with exactly four ASCII letters, case-insensitively. They do not select a city or organisational room. Only the authenticated mesa adds proposals, within its selected city and room. `/mesa` stays unlinked from the participant interface. There is no public proposal-submission page or participant agenda in this flow. Historical proposals, categories, supports and results remain stored.

Opening a proposal reserves its code in the same write transaction as the status transition. `vote_codes` maps one code to one proposal, with a case-insensitive unique constraint shared across cities and rooms. Four independently uniform random letters provide 456,976 possible codes. Allocation retries collisions up to 64 times and fails without opening the vote if no candidate is reserved. This finite namespace is never recycled: closed codes keep identifying their original result. No deletion, reassignment, rotation or replacement-vote operation is introduced.

The additive migration reserves codes for already-open votes. It leaves existing closed results accessible to the mesa and preserves all original proposal fields, rooms, counts, active receipts and current database-backed mesa sessions. The password migration still intentionally revokes legacy sessions on first credential initialization. No production database is copied or reset for testing.

`POST /api/votes/enter` resolves the proposal code. It sets a shared HttpOnly, SameSite=Strict session cookie scoped to `/api/votes` (Secure on HTTPS), authenticated with the existing stable server secret. This cookie is identical for everyone admitted to that proposal; it has no participant identity. `GET /api/votes/session` returns only that proposal and its city context, never other proposals, room codes or open totals. Vote and receipt-status actions verify the requested proposal matches the grant. Old room admission and `/api/rooms/proposals/:id/vote` cannot authorize formal voting. Legacy room reads/support APIs remain compatible; proposal creation through `/api/rooms/proposals` is explicitly forbidden, including anonymous requests. Mesa writes retain transaction-level checks of session expiry, credential version, city and room ownership.

An admitted open vote has no in-app switching action. A different-code entry or leave request using that grant is rejected while it is open; this is flow control, not strong authentication. Normal Back, tab closing and browser controls work. Reloading resumes the same proposal. Once closed, the participant sees its digital, physical and combined final counts inline, with an explicit back-to-start button. A later vote in the room never replaces that result. Re-entering an old closed code also shows its original result. Results are counts only; closure remains irreversible and requires saved physical totals.

A vote receipt is independent of admission: re-entry, expiration of the shared admission cookie and additional normal tabs reuse the same per-proposal browser receipt. Web Locks coordinate creation and sends where available; without them cross-tab coordination remains best effort. Receipts store a random value and sent flag, never the choice, and are not reused between proposals. Refresh reconciles an unconfirmed receipt against the server, covering a lost success response without automatically submitting again. The server consumes its hash and increments counts atomically. Closure removes the server receipt records in the same transaction as final publication.

The old 24-hour client expiry is removed because an open vote could otherwise gain a fresh receipt. The browser removes a receipt when it observes that proposal's closure. A browser that never returns may retain a stale receipt; the privacy details explain this. There is no background cleanup while the browser is closed, no server participant history, and no forensic or backup-deletion promise. Clearing storage, changing browsers, private windows or modifying the client bypass the accepted repeat restriction. Shared four-letter codes prove neither identity nor physical presence. The application does not collect participant IPs, forward browser headers to Turso, add analytics or request geolocation; the existing Vercel connection-IP limitation remains in the privacy details.

The feature uses the existing HTML/CSS/JavaScript, Node and libSQL infrastructure with no new dependency or external service. Tests and screenshots use isolated local fixtures. PRs remain open for review; this change does not authorize a production release.
